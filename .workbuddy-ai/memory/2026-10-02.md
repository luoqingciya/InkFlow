## 踩到的坑（都已在文档里记录）

### 1. `uv sync` 不装 workspace 成员

`uv sync` 默认只装根项目依赖，6 个成员包一个都不装。
必须 `uv sync --all-packages`。已写进 README 与 setup.md。

### 2. 内存 SQLite 的多连接隔离

测试用 `sqlite:///:memory:` 会导致随机的 `no such table` ——
SQLite 的内存库是「每连接一个独立数据库」，连接池换连接就看不到表。
改用临时文件数据库。

### 3. 代理环境变量劫持 127.0.0.1

开发机上的 `http_proxy` 会把发往 mock 站点的请求也转出去，
症状是「mock 站点连不上」，看起来像服务没起。conftest 里统一清除。

### 4. YAML 双引号里的 `\S` 是非法转义

`regex: "作者：(\S+)"` 会直接让 YAML 解析失败。正则必须用单引号。

### 5. XPath 的 `@class="x"` 是精确匹配

节点上还有别的类名（`class="book-item odd"`）就匹配不上，要写 `contains(@class,'x')`。

## 版本号统一为 0.1.0.dev0（改成了单一来源）

用户要求把版本号统一为 `0.1.0.dev0`（PEP 440）。借这次机会把原本
**14 处分散定义**（7 个 pyproject + 6 个 `__init__.py` + 1 个 package.json）
改成单一来源：

- 唯一手写点：`packages/inkflow-core/src/inkflow_core/__init__.py` 的 `__version__`
- 成员包 pyproject：`dynamic = ["version"]` + `[tool.hatch.version] path`
  **跨目录**读取 core 的 `__init__.py`（实测可行）
- 成员包 `__init__.py`：`from inkflow_core import __version__` 转发
- 根 pyproject：展示用，与来源一致
- 桌面端：npm 是 semver 生态，用等价写法 `0.1.0-dev.0`
- 新增 `scripts/check_version.py`，已接入 `scripts/check.py` 与 CI

实测结果：`uv sync --all-packages` 后 6 个包全部为 `0.1.0.dev0`，
运行时 `import inkflow_*.__version__` 也全部一致。

副作用（已写进 ADR-014 与 setup.md）：成员包用了动态版本，
不能脱离 workspace 单独 `pip install`。

## 上线 GitHub + CI/CD

仓库：**https://github.com/luoqingciya/InkFlow**（public，SSH remote）

### 流水线

- **CI**（push / PR）：版本号一致性 → ruff → mypy → pytest，矩阵 Ubuntu + Windows；
  另有桌面端类型检查与构建
- **Release**（push tag `v*`）：三平台 PyInstaller 打包后端 → **冒烟测试** →
  取回对应平台后端 → electron-builder 打安装包 → 创建 Release

### 关键设计

- **PyInstaller 不能交叉编译**，所以后端必须在三个平台各打一次
- **打包后立刻冒烟测试**：PyInstaller 的失败往往是静默的（构建成功、
  一运行就 ModuleNotFoundError），只看「构建通过」会把问题漏给用户
- 桌面端生产模式直接执行随包分发的后端，不再依赖用户机器上的 `uv`
- 图标用 `scripts/make_icon.py` 纯标准库生成（可复现、可调色），
  没有引入图像处理依赖，也没消耗图像生成额度

### 实测结果

```text
dist/inkflow-server.exe   28.2 MB（单文件）
冒烟测试：
  [后端] INKFLOW_READY port=63648 token=...
  [健康检查] {"status":"ok","version":"0.1.0.dev0","uptime_seconds":0.11}
冒烟测试通过
```

### 第一次 CI 失败（三个问题，根因都是「改完没本地验证就提交」）

1. **Windows runner 控制台编码**
   `UnicodeEncodeError: 'charmap' codec can't encode` —— GitHub Actions 的
   Windows 环境 stdout 默认是 cp1252，脚本打印中文直接崩。
   修复：脚本入口 `sys.stdout.reconfigure(encoding="utf-8")` 兜底 +
   CI 设 `PYTHONUTF8=1`（PEP 540 的 UTF-8 模式，比只设 PYTHONIOENCODING 彻底）
2. **`make_icon.py` 未格式化** —— 写完脚本没跑 `ruff format` 就提交
3. **TS 类型错误** —— `stdio: ['ignore','pipe','pipe']` 时 spawn 返回
   `ChildProcessByStdio<null, Readable, Readable>`，断言成
   `ChildProcessWithoutNullStreams` 不成立（stdin 是 null）。

教训：`scripts/check.py` 原先只覆盖 Python 侧，改完前端不会报错。
已给它加上前端类型检查（有 node_modules 就跑）。

### Release 流水线的两个坑

1. **Windows runner 的默认 shell 不是 bash**：`ls -la` 会交给 PowerShell，
   而 PowerShell 里 `ls` 是 `Get-ChildItem` 的别名，不认识 `-la` 参数，
   报 "A parameter cannot be found that matches parameter name 'la'"。
   跨平台命令必须显式写 `shell: bash`。
2. **后端产物同名互相覆盖**：Linux 与 macOS 的 PyInstaller 产物都叫
   `inkflow-server`，汇总到同一目录时后写入的覆盖先写入的，
   最终 Release 里只剩一个。修复：按平台重命名后再汇总。

### 踩坑

- **spec 里的相对路径是相对运行时 cwd**，不是 spec 文件所在目录。
  要用 PyInstaller 注入的 `SPECPATH`，否则从仓库根跑会找不到入口
- **Windows 上进程刚终止时文件句柄未释放**，删临时目录会 PermissionError。
  冒烟测试用 `TemporaryDirectory(ignore_cleanup_errors=True)` ——
  要验证的是「后端能不能起来」，不是「临时目录能不能删干净」

## 便携化改造 + CLI 打包（版本 → 0.1.0.dev1）

### 数据目录便携化（ADR-015）

解析顺序：`INKFLOW_HOME` → 运行目录下的 `.inkflow` → `~/.inkflow`

「运行目录」：PyInstaller 打包后是**可执行文件所在目录**
（不是进程 cwd —— 从快捷方式启动时 cwd 可能是任意位置），源码运行是当前工作目录。

不可写时逐级回退（macOS 的 `.app` 内部、部分 Linux 安装位置只读）。
桌面端自己探测可写性后，显式把 `INKFLOW_HOME` 传给后端。

**实测**：把两个 exe 拷到独立目录运行，`.inkflow/` 出现在该目录，
完整流程（导入书源 → 搜索 → 下载 6/6 章 → 导出 EPUB）跑通，
产物落在 `./.inkflow/exports/`。

### CLI 现在有独立打包产物

原先只打包后端，CLI 只能靠 `uv run`。现在 `packaging/inkflow-cli.spec`
产出单文件 CLI，与后端一起发布。

### 踩到的两个真实问题

1. **`inkflow_core.__init__` 无条件导入 storage** → 打包 CLI 时报
   `ModuleNotFoundError: sqlalchemy`。CLI 是纯 HTTP 客户端，用不到数据库层。
   改成 PEP 562 的模块级 `__getattr__` 惰性导出 `Database`。
   产物对比：CLI 18.9 MB vs 后端 28.2 MB。
2. **打包的 CLI 在 Windows 上管道输出是 GBK** —— 终端里看着完全正常，
   接给别的程序按 UTF-8 解码就乱码。只有**管道重定向**时才暴露，
   直接看终端永远发现不了。CLI 入口统一 `reconfigure(encoding="utf-8")`。

### Windows 免安装版改 zip

portable.exe 每次运行会自解压到临时目录，数据目录反而落不到程序旁边；
zip 解压后就是一个完整目录，整个文件夹拷走即可迁移 —— 与便携化目标一致。

## 桌面端实机验证（v0.1.0-dev1）

第一次把打包的 Electron 应用真正跑起来，验证了主进程能拉起内嵌后端。

### ⚠️ 本机环境陷阱：`ELECTRON_RUN_AS_NODE=1`

这个环境**预设**了 `ELECTRON_RUN_AS_NODE=1`，它让所有 Electron 可执行文件
退化成 Node 运行 —— 不加载 GUI、不执行应用代码。

**症状**：打包的 Electron 应用启动后进程存在但什么都不做
（无窗口、无日志、不创建数据目录）。加 `--no-sandbox` 会报
`bad option: --no-sandbox` —— 这是 **Node** 的错误格式，不是 Electron 的，
看到这个就该怀疑变量被设了。

排查时我先怀疑了主进程代码、asar 打包、electron-builder 配置，全都不是。
**以后验证 Electron 应用必须先清掉这两个变量**：

```bash
env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS ./InkFlow.exe
```

CI 上没有这个变量，所以 CI 打包不受影响。

### 本机 `npx electron .` 不可用

npm 的 allow-scripts 策略阻止了 electron 的 postinstall，
二进制没下载，`npx electron .` 报 "Electron failed to install correctly"。
开发模式调试只能靠 `npm run dev`（electron-vite 走另一条路径）。

### 构建产物删不掉的真正原因

打包后清理 `desktop/release/`、`desktop/build-*/` 时报
「另一个程序正在使用此文件」，`tasklist` 里却找不到任何 inkflow / electron 进程。
我一度往「electron-builder 锁文件」「杀毒软件」「文件索引服务」方向排查。

**实际是 WorkBuddy 自己**在监视工作区、持有文件句柄（洛清辞指出）。
停掉进程后等一会儿重试就能删干净 —— 本次 6 个目录最后全部删除成功。

### 顺带修的配置错误

electron-builder 的 schema **没有顶层 `zip` 属性**（zip 只是 target 类型，
没有独立配置节）。我写了 `zip: artifactName:` 导致 macOS 打包直接报
"configuration has an unknown property 'zip'"。

已在 CI 的 desktop job 加一步 `electron-builder --dir` 校验配置 ——
这类错误不该等到发版才暴露。

### 产出

  正文入库与清洗、EPUB 结构合法性、逐章明细、跳过已下载、失败隔离、

- `tests/integration/test_websocket.py`（16 项）：snapshot 首帧与字段形状、
  事件流、终态关闭、4404/4401、Broker 语义、多订阅者

- `library` 夹具重构为 `_Library` NamedTuple（返回 client + book_id）

### 发现并修复的真实 API 缺口

**`auto_start=false` 建出的任务原先没有任何端点能启动它** ——
`resume` 只接受 `PAUSED`。补了 `POST /api/v1/tasks/{id}/start` 与
CLI `inkflow task start`。

### 关键认知：TestClient 的 portal 隔离

`TestClient` **每个 HTTP 请求都新起一个 anyio portal**（独立事件循环），
请求返回即销毁；WebSocket 会话跑在自己的 portal 里。
所以「用 REST 启动任务 → 用 WebSocket 收进度」在 TestClient 下**必然挂死**。

解法：流式用例改用 `live_server` 夹具 —— 后台线程跑真实 `uvicorn.Server`，
配 `websockets` 客户端，让 REST 与 WS 共享同一事件循环。

### ⚠️ 本机环境陷阱：pytest 退出码会被 safe-delete 守门器干扰（花了两小时才看清）

**两个现象，同一个根因**（宿主注入的 `sitecustomize.py` 守门器）：

1. **全量 pytest 偶发 exit 1**，但 stdout 里**一个 `F` 都没有**，
   也不打印 summary（`157 passed` 那行）。单独跑文件则 40 次全过。
   → teardown 要删 `%TEMP%\pytest-of-<user>\garbage-*`（累积 100+ 个），
   批量删除触发 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（阈值 50）→ `SystemExit(1)`。
2. **`--basetemp` 指向工作区内目录 → 稳定 `151 errors`**（只有 6 passed，14s 退出）。
   守门器把 basetemp 下的 `…current` 符号链接解析成整个工作区，
   报 `count: 1175 · targets: [".pt_d\test_...current"]` → 连 fixture setup 都进不去。

**测试本身全绿。**

**误判过程**（值得记住的教训）：
- 我把它当成真实测试失败，用「全量连跑 N 次」当探针 —— 每次 3 分钟，
  跑了两个多小时，始终没抓到 traceback（因为根本没有 traceback）
- 中途还被自己 `kill` 掉的 pytest 残留目录干扰，误以为 basetemp 复用是原因

**正确做法**：
1. **先看 stdout 是否真的含 `F`**。没有 `F` 却 exit≠0 → 不是测试失败
2. **stdout / stderr 分开重定向** + `-x --tb=long`，让守门器的消息现形
3. **别用「多跑几次碰运气」查偶发失败** —— 先从代码语义推理，
   或者改断言让它吐出诊断信息，一次拿真相

**命令**（basetemp 必须放工作区之外）：
```bash
uv run pytest -p no:cacheprovider --basetemp="$TEMP/inkflow_pt_$RANDOM"
# 157 passed
```
