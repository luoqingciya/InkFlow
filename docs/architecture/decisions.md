# 设计决策记录（ADR）

每条决策包含「背景 / 决策 / 后果」。**后果一栏要写代价**，只写好处的 ADR 没有价值。

新增决策时追加到末尾，不要修改历史条目 —— 决策变了就写新的一条并标注取代关系。

---

## ADR-001 采用 API-First 架构

**背景**
传统小说下载器把搜索、请求、解析、下载、GUI 写在一起，导致换 GUI 要重写业务层、
书源规则与业务逻辑互相污染、下载任务无法统一管理、也无法给第三方客户端复用。

**决策**
所有核心能力先定义 HTTP 接口（`/api/v1`），CLI 与桌面端都只是这个接口的客户端。
UI 不直接 import 业务代码。

**后果**

- 好处：业务核心只有一份；新增入口（Web / Bot / 插件）不需要改核心；
  接口契约可用 OpenAPI 导出，桌面端的类型可以生成而非手写。
- 代价：桌面端多了一层 HTTP 通信，本地调用也有序列化开销；
  开发时要同时起两个进程；进程间需要端口协商与鉴权（见 ADR-011、ADR-013）。

## ADR-002 内核兼容 + 外层隔离

**背景**
Legado 书源生态很大，直接支持能立刻获得大量可用书源。但 Legado 是 GPL-3.0 项目，
且其规则语义会随版本演进。若把兼容逻辑散落在业务代码里，规则一变就要全项目回归。

**决策**
兼容的是 Legado 的**数据结构与规则语义**，不是复制其实现。
全部兼容代码关在 `inkflow-legado` 一个包里，通过工厂注册接入 Source Engine。

**后果**

- 好处：Legado 规则变化只需升级一个包；Core / API / CLI / Desktop 完全不受影响；
  许可证边界清晰（见 [licensing.md](../development/licensing.md)）。
- 代价：需要维护一层 DSL → AST 的编译（见 ADR-005）；
  兼容层与真实 Legado 的行为差异需要靠测试集持续校准。

## ADR-003 用 uv workspace 管理多包

**背景**
项目天然分层（core / source / legado / api / cli / export），
如果做成单包，依赖方向只能靠约定维持，很容易出现 core 反向 import api 的情况。

**决策**
用 uv workspace 拆成 6 个包，依赖写在各自的 `pyproject.toml` 里。

**后果**

- 好处：依赖方向由构建系统强制；可以单独测试与发布某个包；
  将来开源某个包（如 `inkflow-legado`）不需要拆分仓库。
- 代价：`uv sync` 默认只装根依赖，必须用 **`uv sync --all-packages`**；
  新增包要同时改根 `pyproject.toml` 的 `members` 与 `[tool.uv.sources]`。

## ADR-004 原生书源用声明式 YAML，不写代码

**背景**
书源需要一种「容易写、容易查错」的形态。如果原生书源也允许写代码，
就立刻面临沙箱、资源限制、调试困难等一整套问题。

**决策**
原生书源（Level 1）只描述「请求什么、从哪里取什么」：
URL 模板 + CSS/XPath 选择器 + 取值动作 + 正则。不提供代码执行能力。

**后果**

- 好处：类型安全、可静态校验、性能最高、出错时错误信息直指某个选择器。
- 代价：复杂站点（需要签名、加密、多步交互）无法用原生书源表达，
  必须走 Legado JS（L2）或浏览器（L3）。

## ADR-005 Legado 规则编译成 AST，不直接执行

**背景**
Legado 规则是一套自定义 DSL（`class.x@tag.a@text##正则##替换`）。
最直接的实现是在适配器里堆 `if` 分支逐段解析并执行，但那样规则语义会渗进业务代码。

**决策**
规则先被 `LegadoRuleCompiler` 编译成统一的 `Rule` 对象（模式、选择器链、
取值动作、替换链、备选链），再由执行器求值。

**后果**

- 好处：规则可在执行前被检查、被展示（Source Debugger）、被单元测试覆盖；
  执行逻辑只有一份，不随规则语法增长而膨胀。
- 代价：多了一层编译；编译期的语法判断需要持续补充（例如
  「只有一段的 `text` 是取值动作而不是标签选择器」这类规则）。

## ADR-006 章节元数据与正文分离存储

**背景**
正文数据量远大于目录。如果放在同一张表，列目录时会把几 MB 正文拉进内存。

**决策**
`chapters` 存目录，`chapter_contents` 存正文，两者以 `chapter_id` 关联。
正文同时保留 `raw_content`（清洗前）与 `clean_content`（清洗后）。

**后果**

- 好处：列目录轻量；改清洗规则时可以只重算 `clean_content`，**不必重新抓取**；
  清洗算法改坏时能回到原始数据。
- 代价：存储翻倍（正文存两份）。对个人工具而言这个代价可以接受。

## ADR-007 下载任务化，状态机放在领域层

**背景**
`for chapter in chapters: download(chapter)` 无法支持暂停、恢复、取消、进度查询、
失败重试，也无法在重启后继续。

**决策**
下载建模为 `DownloadTask` + `DownloadTaskItem`，状态转换规则定义在模型里
（`TASK_TRANSITIONS`），非法转换抛 `TaskError`。

**后果**

- 好处：状态一致由模型保证，调度器不需要防御各种「理论上不该出现」的状态；
  任务可持久化，重启后可恢复。
- 代价：多两张表与一套状态机；暂停语义需要仔细定义
  （当前实现：已在途的章节跑完，不再开始新章节）。

## ADR-008 SQLite + JSON 文本存嵌套结构

**背景**
书源的 `request` / `meta` / `raw` 是嵌套对象。用关系表拆开会让 schema 复杂且僵化
（Legado 书源有大量自定义字段）。

**决策**
MVP 阶段用 SQLite；嵌套结构以 JSON 文本整存整取。

**后果**

- 好处：零运维、单文件、迁移简单；书源自定义字段不会撑爆 schema。
- 代价：无法按嵌套字段做 SQL 查询（当前也不需要）；将来换 PostgreSQL
  只需换连接串与少量方言细节。

## ADR-009 手写 EPUB 生成，不引入电子书库

**背景**
生成 EPUB 需要处理 OPF / NCX / XHTML / zip 结构。已有 `ebooklib` 之类的库。

**决策**
用标准库 `zipfile` 手写 EPUB 3（同时带 NCX 兼容旧阅读器）。

**后果**

- 好处：少一个依赖就少一份许可证审查与打包体积；
  EPUB 结构完全可控（例如保证 `mimetype` 是首个未压缩条目）。
- 代价：需要自己维护 EPUB 规范的实现细节；将来支持 EPUB 2 特有特性时成本更高。

## ADR-010 本地 API 用 session token 鉴权

**背景**
服务监听 `127.0.0.1`，但本机上**任何**进程都能访问回环端口 ——
浏览器里的一个恶意页面就能对着 `127.0.0.1:8765` 发请求。

**决策**
每次启动生成一次性 session token，所有非公开路由要求
`Authorization: Bearer <token>`。只有 `/health` 与文档免鉴权。

**后果**

- 好处：把「本机可访问」收窄到「持有 token 的进程可访问」。
- 代价：客户端必须先拿到 token（见 ADR-013）；WebSocket 因为浏览器 API
  限制只能用查询参数传 token。

## ADR-011 Renderer 不接触 Node 权限

**背景**
Electron 的默认配置里 Renderer 可以 `require('child_process')`。
一旦页面被注入脚本，等于把整台机器交出去。

**决策**
`contextIsolation: true` + `nodeIntegration: false`，
只通过 preload 的 `contextBridge` 暴露具名接口（连接信息、打开路径、
文件对话框、读文本文件），并在页面层加 CSP 限制可连接的地址。

**后果**

- 好处：攻击面从「整个 Node」缩小到「几个具名方法」。
- 代价：任何新的系统能力都要显式加一个 IPC 通道并想清楚参数校验；
  Renderer 不能直接读文件，导入书源要绕一层主进程。

## ADR-012 书源 ID 由地址派生（幂等导入）

**背景**
如果每次导入都生成随机 ID，同一书源重复导入会在列表里堆出多条记录，
而且已下载的书籍会与新导入的书源「失联」。

**决策**
`stable_id("src", 书源地址)` —— 用地址的 SHA256 前缀作为 ID。
原生书源与 Legado 书源共用同一套规则。

**后果**

- 好处：导入天然幂等；同一书源重复导入是「更新」而不是「新增」。
- 代价：同一地址下的两个不同书源无法共存（当前场景下不是问题）；
  地址变更会被视为新书源。

## ADR-013 端口 0 + 握手文件做进程间协商

**背景**
桌面端要拉起后端并与之通信，但端口不能硬编码（会冲突），
token 也不能硬编码（见 ADR-010）。

**决策**
后端默认 `port = 0`（由系统分配），就绪后在 stdout 打印固定格式的一行：

```text
INKFLOW_READY port=53421 token=xxxxx
```

同时写入 `~/.inkflow/server.json`（供 CLI 自动发现），退出时删除。

**后果**

- 好处：多实例不冲突；Desktop 与 CLI 都能可靠拿到实际端口与 token。
- 代价：端口无法从配置预知，只能通过握手获得；
  `server.json` 是「服务正在运行」的信号，异常退出可能残留（已做退出清理）。

## ADR-014 版本号单一来源，格式为 PEP 440

**背景**
项目有 6 个 Python 包加一个 Electron 应用。如果每个包各自写版本号，
发版时要改 14 处（7 个 pyproject + 6 个 `__init__.py` + 1 个 package.json），
漏改任何一处都会导致「包版本与实际代码不符」—— 这类问题不出事则已，
出事时很难查（用户报的版本号与开发者以为的不一样）。

**决策**

唯一来源：`packages/inkflow-core/src/inkflow_core/__init__.py` 的 `__version__`。

```text
inkflow_core.__version__        ← 唯一手写的地方
        │
        ├── 各成员包 pyproject    [tool.hatch.version] path 跨目录读取
        ├── 各成员包 __init__.py  from inkflow_core import __version__
        ├── 根 pyproject          展示用，与来源保持一致
        └── desktop/package.json  semver 等价写法
```

版本号格式用 **PEP 440**（如 `0.1.0.dev0`），因为它是 Python 打包工具链的规范。

**后果**

- 好处：发版只改一处；构建元数据与运行时 `__version__` 不可能不一致；
  `scripts/check_version.py` 能在 CI 里拦住硬编码与漂移。
- 代价：成员包的 pyproject 用 `dynamic = ["version"]`，
  **不能直接 `pip install ./packages/inkflow-api`** —— 单包构建时
  hatch 需要能读到 `../inkflow-core/`，脱离 workspace 会失败。
  本项目始终在 workspace 内构建，可以接受。
- 代价：桌面端是 npm 生态，必须用 semver。两种规范的映射写在
  `scripts/check_version.py` 的 `to_semver()` 里（`.dev0` → `-dev.0`）。

## ADR-015 数据目录便携化：运行目录优先

**背景**
原先数据固定在 `~/.inkflow`。对个人工具来说这带来两个问题：把程序目录拷到
另一台机器后数据不会跟着走；想「整个应用装进 U 盘」也做不到。
Windows 的免安装版尤其别扭 —— 程序是绿色的，数据却写进了用户主目录。

**决策**
数据目录按优先级解析：

```text
1. INKFLOW_HOME 环境变量        （显式指定：测试、特殊部署）
2. 运行目录下的 .inkflow        （便携模式）
3. ~/.inkflow                  （兜底）
```

「运行目录」的判定：PyInstaller 打包后是**可执行文件所在目录**
（不是进程 cwd —— 从快捷方式启动时 cwd 可能是任意位置），源码运行是当前工作目录。

第 3 步不是多余的：macOS 的 `.app` 内部、部分 Linux 安装位置是只读的，
硬往里写只会让程序起不来。桌面端会自己探测可写性，再显式把
`INKFLOW_HOME` 传给后端。

**后果**

- 好处：便携 —— 拷走整个目录即可迁移；数据位置可预期（就在程序旁边）。
- 好处：Windows 免安装版换成 zip 后，解压目录就是一个自包含的应用。
- 代价：**CLI 在不同目录运行会用到不同的数据目录**，与 Desktop 默认不共享。
  缓解办法是放在同一目录；CLI 也会在所有候选目录里找 `server.json`，
  找得到就能连上。
- 代价：多了一层可写性探测与回退，行为不像「固定路径」那样一眼可预期。
  因此 `inkflow-server` 启动时会打印实际使用的数据目录。

## ADR-016 失败章节按轮次重试，不使用逐章独立退避

**背景**
任务层原先没有重试：HTTP 层会重试「同一请求」的网络错误与 5xx，
但一旦某章被判定失败，它就永久留在失败名单里。而站点抽风、限流、
CDN 抖动这类问题往往「这次不行、过几秒就行」，缺了任务层重试就会
留下永久的缺口，用户只能手动重跑整本书。

**决策**
`_execute` 改为**按轮次**驱动：

```text
第 0 轮：下载全部待下载章节
   ↓ 收集失败章节（成功的不再入队）
第 1 轮：只下载上一轮失败的
   ↓ …直到轮次用尽或全部成功
第 N 轮
```

- 轮数来自 `download.retry`（默认 3），轮间等待 `retry_backoff * 2^n`。
- **每轮开始前把上一轮的失败计数减回去**：重试成功了就该不留错误痕迹。
- 重试成功时清空该章 `item.error`，但 `attempts` 保留真实的累计次数。
- 取消不进重试队列 —— 取消是用户的明确意图，不是故障。

**后果**

- 好处：瞬时故障自愈，用户不必手动重跑；`failed` 的语义变成
  「重试额度用尽后仍失败」，更接近用户理解。
- 好处：轮次式重试天然带「波动收敛」效果 —— 同一轮内不会重试，
  避免了对已限流的站点持续加压。
- 代价：**失败的任务整体耗时变长**。6 章里有 1 章一直失败的极端情况下，
  总耗时是「首次 + N 轮退避之和」。因此退避基数默认 1s，且轮数上限 10。
- 代价：`failed` 计数在轮次之间会先减后加，中间瞬间读到的是**偏低**的值。
  读取方（进度条）需要容忍 `completed + failed < total` 的中间态。

## ADR-017 缓存实现在装配层，只缓存 GET，按 LRU 淘汰

**背景**

`HttpCache` 协议、`HttpClient` 里的读写逻辑、`http_cache` 表、
`cache` 配置段全都齐了 —— 唯独**没有默认实现**，所以缓存从未生效过。
补上它之前要定三件事：实现放哪、缓存什么、怎么淘汰。

**决策**

**1. 实现放 `inkflow-api/services/cache.py`，不放 `inkflow-source`。**

协议在 source 定义，但缓存要落 SQLite，而 source 不依赖 sqlalchemy ——
它是「书源引擎」，不该背持久化职责。装配层同时依赖 core（有 `Database`）
和 source（有协议），是唯一合适的位置。依赖方向仍是 `core ← source ← api`。

**2. 只缓存 GET。**

`_cache_key` 里含 method，GET / POST 不会互相串味，但 POST **自己**会被缓存 ——
那是有副作用的请求，复用旧响应等于返回错误结果。在 `HttpClient.request`
里显式限制为 GET，而不是指望调用方每次都记得传 `use_cache=False`。

**3. 按 LRU 淘汰，不做 TTL 清扫任务。**

- 淘汰依据是 `hit_at`（最近命中时间），从未命中的条目按 `created_at` 排 ——
  它是最该被淘汰的那批。
- 过期条目**惰性删除**：读到就扔。没有后台清扫协程，也就没有它的生命周期问题。
- 未命中的过期条目靠 LRU 逐渐挤掉，不额外扫全表。

**4. `enabled=false` 或 `http_ttl<=0` 时返回 `None`，不构造空转对象。**

`HttpClient` 的 `cache` 参数本来就是 `None` 表示不缓存，直接复用这个语义，
比构造一个「什么都不做」的缓存更省事，也不会在 `system_info` 里
报告一个假的「已启用」。

**后果**

- 好处：同一页面在 TTL 内只抓一次，重复抓取与限流压力都降下来。
- 好处：书源引擎保持纯粹 —— 它只认识协议，不关心落盘。
- 代价：**LRU 淘汰要算一次 `SUM(size)`**。条目数万级时是毫秒级，
  但如果将来把 `max_size` 调到几十 GB，`set` 会开始变慢。
  真到那时再换成维护计数器，现在不提前优化。
- 代价：**未被访问的过期条目会滞留**，直到被 LRU 挤掉。
  换来的是零后台任务，以及「不做全表扫描」的可预测开销。
- 代价：桌面端若想独立使用缓存需自行装配。CLI 是纯 HTTP 客户端，
  不直连数据库，用不到这一层。

## ADR-018 日志用自管 handler，不依赖 basicConfig

**背景**

`log` 配置段（级别 / JSON Lines / 轮转）与 `paths.logs_dir` 早已就位，
但**没有任何代码安装 handler** —— 日志从来没落过盘。那两处
`logging.getLogger("inkflow.api")` 实际走的是 Python 的 last-resort handler，
只在 stderr 打一条无格式的消息，进程一退就没了。

**决策**

**1. 不用 `logging.basicConfig`。**

它只在 root logger **尚无 handler** 时生效。而 uvicorn 启动时会抢先装自己的
handler，于是我们的配置被**静默忽略** —— 症状是「配置写了、代码也调了，
日志就是没落盘」，而且不报任何错。改为显式 `addHandler`。

**2. 启动 uvicorn 时传 `log_config=None`。**

uvicorn 默认给 `uvicorn` / `uvicorn.access` 配的 logger 是 `propagate=False`，
日志会**截在它自己那里**，root 上的文件 handler 永远收不到。
传 `log_config=None` 让它不装 handler，日志自然向上冒泡到 root。

**3. 文件 handler 挂 root，不挂 `inkflow`。**

否则 uvicorn 与其他库的日志都不落盘。挂 root 才能「一次配置，全进程生效」；
级别由配置控制，所以不会因为挂 root 就被第三方库的 DEBUG 刷屏。

**4. 写不进去不抛错。**

日志目录只读（macOS 的 `.app` 内部、部分 Linux 安装位置）时降级为
仅控制台输出，服务照常启动。日志是辅助设施，不该带走主流程。

**5. `encoding="utf-8"` 必须显式指定。**

Windows 默认 cp1252，中文日志会乱码甚至抛 `UnicodeEncodeError`。

**后果**

- 好处：日志真的落盘，且 **uvicorn 的启动日志也在里面** ——
  排障时「服务起不来」这类问题终于有东西可查。
- 好处：`json_logs=true` 时每行一条独立 JSON，可直接接日志采集器；
  `extra={...}` 传的业务字段（如 `task_id`）会被一并输出。
- 好处：`delay=True`，没日志就不产生空文件。
- 代价：**root logger 是进程级状态**。测试必须还原 handler，
  否则用例之间互相污染（前一个用例的 handler 把日志写进它的临时目录）。
  已用 autouse fixture 处理。
- 代价：日志随数据目录走（`logs/inkflow.log`），换目录即换日志 ——
  这与 ADR-015 的便携化目标一致，但意味着**没有全局的日志汇聚点**。

## ADR-019 封面与插图下载：只做「拿到字节」，不改正文格式

**背景**

`Book.cover_url` 早就在抓，`ExportRequest` 也早就有 `cover_bytes` 字段、
EPUB 导出器也完整支持封面 —— 但**没有任何代码把这两端接起来**，
所以导出的 EPUB 从来没有封面。`ContentResult.images` 同理：
适配器收集了图片地址，然后没人用，直接丢掉。

**决策**

**1. 封面：缺的时候补抓一次详情页。**

关键发现：**封面只存在于详情页规则里，搜索结果里没有**。
不补这一步，「封面下载」永远不会生效 —— 除非用户恰好手动翻过详情页。
所以导出前若 `book.cover_url` 为空，就抓一次 `book_info` 并回写。
已经有封面就不重复请求。

**2. 封面失败不阻断导出。**

封面是锦上添花。拿不到就打 warning 然后继续 —— 不该因为它
让整本书的导出失败。这一点与「不静默降级」不冲突：
**降级要留痕**，所以是 warning 而不是默默跳过。

**3. 插图：从 `raw_content` 提取地址，存到本地。**

清洗后的 `clean_content` 是纯文本，`<img>` 标签在那一步就被抽掉了；
只有 `raw_content`（原始 HTML）还留着图片位置。地址可能是相对路径，
用 `chapter.url` 做 `urljoin` 补全。

**4. 插图只下载到本地，不嵌进 EPUB。**

这是刻意的取舍，见下。

**后果**

- 好处：导出的 EPUB 终于有封面了，且**不需要用户先手动看详情页**。
- 好处：插图不再被丢弃，落盘在 `.inkflow/books/<id>/images/`，
  用相对地址去重，重跑不重复下载。
- 好处：资源请求复用书源的 `HttpClient`（同一套超时 / 限速 / SSRF 防护），
  并且带上书源的 headers —— 不少站点有图片防盗链，带 Referer 反而更容易拿到。
- **代价：EPUB 里看不到插图。** 图片在磁盘上，但阅读器里没有。
  要让插图出现在正文中，需要让正文**保留图片位置**，也就是
  `clean_content` 不能是纯文本 —— 那是「正文格式」的架构改动，
  会影响三个导出器与 normalizer 的契约。

  **这一项已决定不做**（2026-10-03）：插图对小说阅读的收益不足以支撑
  那个改动面。图片仍会下载到本地，用户可以在 `.inkflow/books/<id>/images/`
  里找到它们。若将来确实需要，应作为独立的设计议题重新评估，
  而不是顺手改掉正文格式。
- 代价：封面补抓会在导出前多一次网络请求（仅当缺封面时）。

## ADR-020 JS 规则跑在独立 Node sidecar，vm 只做隔离与超时

**背景**

Legado 的 L2 书源用 ``@js:`` 规则做签名、加密、多步请求。
在此之前编译器把这类规则编成 ``RuleMode.JS`` 就**静默跳过** ——
字段解析出来是空的，用户以为「这个网站没这个字段」，其实是书源没跑起来。

执行不可信的书源 JS 需要回答三个问题：跑在哪、怎么限制、网络请求谁发。

**决策**

**1. 跑在独立进程（Node sidecar），不在 Python 主进程里。**

JS 可能死循环、吃满内存、或者利用引擎漏洞。独立进程意味着它崩了只是自己崩 ——
主进程能发现、能重启、能报错。

**2. 通信是 JSON Lines over stdio，而且是同步的。**

Legado 的 ``java.ajax(url)`` 是**同步**语义（书源是给 Rhino 写的，不会写
``await``）。所以 sidecar 内部用 ``fs.readSync`` 阻塞等响应 —— 单线程、
无 worker、无死锁（Python 是独立进程，阻塞期间能正常处理请求）。

**3. 网络请求回调 Python，sidecar 自己不发请求。**

``java.ajax`` 走反向 JSON-RPC 回到 Python 的 ``HttpClient``。
这样 **SSRF 防护、协议白名单、限速、缓存全部照旧生效**。
让 sidecar 自己联网等于在安全模型上开个洞。

**4. ``node:vm`` 不是安全边界 —— 进程隔离才是。**

这一点必须说清楚，避免后来人误以为有沙箱就安全了：

- ``vm`` 隔离的是**全局变量与作用域**，不是权限。通过宿主函数的
  ``constructor`` 链可以摸到宿主的 ``Function``，进而拿到 ``process``。
  这是 vm 的已知性质，官方文档也这么写。
- **真正的边界是「独立进程 + 进程里没有敏感数据」**：sidecar 里没有数据库、
  没有 token、没有任何凭据 —— 逃逸出去也没东西可拿。
- ``vm`` 在这里只负责两件事：**隔离全局变量**（书源之间不串味）与
  **执行超时**（死循环能被打断）。

**5. 限制分布在三层。**

| 层 | 手段 |
|---|---|
| 进程 | ``--max-old-space-size`` 限制内存 |
| 沙箱 | ``runInContext({ timeout })`` 打断死循环 |
| Python | 兜底超时（sidecar 超时 + 5s），超时即丢弃进程 |

**6. 一个 sidecar 服务所有书源。**

每个书源起一个 Node 进程太浪费（每个约 30MB）。因此 ``host_request``
**按调用传入**而不是绑在实例上 —— 处理器需要知道「现在是谁在请求」，
才能拿到正确的 HTTP 客户端。

**7. 未启用时明确报错，并把解法写进 message。**

``[js] enabled = false`` 时 ``@js:`` 规则抛 ``SOURCE_INVALID``，
message 里直接写「在 config.toml 的 [js] 段设置 enabled = true」。
返回空会把配置问题伪装成解析问题 —— 用户会去查书源，而问题在配置。

**后果**

- 好处：L2 书源可用了，且失败有明确信息。
- 好处：安全约束与 L0/L1 完全一致（同一个 ``HttpClient``）。
- 好处：sidecar 零 npm 依赖，只用 Node 内置模块 —— 不需要 ``npm install``，
  打包也不会多出一堆 ``node_modules``。
- 代价：**需要机器上有 Node.js 20+**。没有时抛 ``JsUnavailableError``，
  明确区分「环境不具备」与「规则写错了」。
- 代价：``vm`` 的隔离强度有限（见上）。要更强隔离得上 ``isolated-vm``，
  但那需要 native 编译，CI 与打包都更麻烦。当前威胁模型下不值得。
- 代价：sidecar 启动有一次性开销（约百毫秒）。已通过复用进程摊掉。

## ADR-021 用真实书源集合校准兼容层

**背景**

M2 完成时，兼容层的测试都是围绕**自己写的** mock 书源。那种测试能证明
「实现符合我的理解」，但证明不了「实现符合真实书源」。

2026-10-03 拿一份 1363 条的真实 Legado 书源集合做体检，发现：

```text
结构解析    1363 / 1363   100%     ← 没问题
规则编译    0 失败                  ← 没问题
选择器求值  8689 / 23481  37.0%    ← 有 37% 的规则根本跑不起来
```

**编译不报错、求值才报错** —— 因为选择器语法是求值时才解析的。
这就是「编译通过」给人的虚假安全感。

**决策**

**1. 体检脚本必须走完整的求值路径。**

最初的体检脚本直接调 `html_parser.select(selector)`，绕过了下标解析，
把合法规则误判成语法错误；后来又只调 `compile()`，漏掉了选择器语法。
**两次都是脚本自己的问题。** 现在统一调 `rule.select_nodes(空文档)` ——
走的是和线上完全一样的路径。

**2. 补齐真实书源里高频出现的三种写法。**

| 写法 | 含义 | 样本数 |
|---|---|---|
| `$.xxx` | **隐式 JSONPath**（不写 `@json:`） | 1400+ |
| `!N` / `!N:M` | 取第 N 个 / 切片 | 443 |
| `.N` / `.-1` | 同上，点号形式；负数从末尾数 | 数百 |
| `{{...}}` | **模板**（不是选择器） | 数百 |
| `[attr=og:x:y]` | 属性值没加引号 | 数百 |

**3. 下标留在选择器串里，求值时再拆。**

`Rule` 不为下标多存字段 —— 反正 CSS 选择器不会以 `!` 或 `.数字` 结尾，
拆解没有歧义。这样 `Rule` 的结构保持简单。

**4. 模板走 `RuleMode.TEXT`，且 `select_nodes` 要跳过非 CSS 模式。**

`RuleMode.TEXT` 是早就预留、一直没用的枚举值，正好给它。
踩过的坑：模板识别对了，但 `select_nodes` 仍拿模板串去解析 CSS ——
**模式判断必须贯穿到求值层**，不能只在编译层做。

**后果**

- 好处：选择器求值失败率 **37% → 5.50%**（改善近 7 倍）。
- 好处：这些写法不是特例 —— 它们合起来占样本的相当比例，
  不认就等于「兼容层只兼容了一半的书源」。
- 代价：`_quote_attr_values` 会对选择器做一次正则改写。**只处理
  「值里含 `:` 或 `|`」的情况**，普通选择器不动，避免引入行为变化。
- 代价：剩余 5.50% 未覆盖。它们多是书源本身写得不规范
  （`?` 在属性值里、`!` 在开头、模板嵌在中间），
  **边际收益递减，暂时不再逐条追**。已记录在 roadmap。

**遗留**

剩余失败类型未逐条修复，属于「已知且接受」的差距。若将来要追，
先按失败模式归类再决定 —— 不要看到一条修一条。
